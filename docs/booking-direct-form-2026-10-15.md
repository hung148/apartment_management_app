# Direct short-stay form (2026-10-15)

User-approved scope: saved-payment edit icons with tooltip only, technical problems inside the short-stay form, and calendar/list booking selection opening the editable form without an intermediate summary page. Follow-up: Technical problems precedes three permanently expanded sections: checkout, cancellation, booking refund. Each has its own reason and explicit confirmation; refund includes amount and payment account. Calendar bubble/opacity/title work remains paused. Long-term payment correction entry points remain unchanged.

## Scenarios and verification checklist

- Active saved bookings open populated; creation/save stays in form; checked-out bookings can reopen. Existing create, pricing, deposit, currency and payment regression coverage retained with old summary-page expectations updated.
- Each receipt icon selects its exact payment ID. Multiple receipts, missing receipt, load error/retry, correction error, uncertain retry with same operation ID, and successful refresh. Corrections retain unsaved guest/notes. Server still validates membership, organization/building/booking scope, collect/refund permissions, revision, amount/date/note, and idempotency.
- Read-only staff cannot change booking fields. Collection-only staff retain collection and correction controls; refund requires its own permission. Cancelled/no-show records show their actual status, with editing/check-out disabled; eligible refunds remain available. Revoked/suspended/cross-organization and v1 access remain denied by existing server authorization.
- Checkout changes status without collection. Each action validates only its own fields; unrelated booking drafts and other action reasons remain intact. Blank reason/amount and refunds above recorded paid amount are rejected locally; server rechecks permissions, revision and refundable balance. Command retries retain the existing operation journal and lock controls against double submissions. Successful command refresh preserves other draft fields. Concurrent receipt edits remain protected by server revision checks.
- Technical problems use the existing room-specific component, including room filtering/report dialog, loading and empty states. Existing behavior hides this component on access/network failure; this change does not alter that behavior.
- New/empty bookings have no saved actions or receipt icons. Stored payment rows with no ledger ID cannot offer an exact correction icon. Server now projects existing ledger IDs; no migration required.
- Responsive populated fixture: two receipts, long Vietnamese guest/note, dates, payment methods, actions and technical section, English/Vietnamese, 320x740, 812x375,1440x900, text scales100/130/200%. Actual-font screenshots under .dart_tool/booking-direct. Check exceptions, reachable icons/actions and vertical ordering. Existing dialog test covers light/dark themes.
- Calendar routing uses existing initialRecordId path; this screen now opens the form for every saved record. Shared calendar layout is not changed. Live calendar click and save behavior require final staging verification.
